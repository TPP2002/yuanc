# Windows 客户端断网保护加固说明

## 原来的缺口与本次修复

以前连接时把三个防火墙配置的默认出站策略设为阻止，但 Windows 的显式允许规则仍然生效。第三方程序安装时创建的允许规则，以及系统自带的“核心网络”允许规则，都可能让流量在隧道内核退出、隧道网卡消失或路由失效后从物理网卡直连。

本次按已批准方案临时停用这些允许规则。连接时的顺序为：先保存三个配置的原始默认策略，再依次设为阻止；记录并停用其他允许规则；创建本项目的节点、隧道网卡、回环、动态地址分配四类放行规则；最后写审计结果。四类放行的地址、端口和网卡口径保持不变，节点切换仍只替换本项目的节点规则。

## 停用范围与先记录的原因

只选本机持久化存储 `PersistentStore` 中当前已启用、出站、允许的规则，排除名称以 `YuanC-KS-` 开头的规则。不会停用入站规则或阻止规则，也不会把连接前已经停用的规则加入恢复名单。

对其他程序和系统规则只执行停用、启用，不删除规则，不修改程序、端口、地址等属性。删除后无法可靠重建原始条件，而保留规则只切换启用状态才能按名单恢复。

必须**先记录，再停用**：把名称列表写入 `run/killswitch-state.json` 的 `disabledRules` 数组，经临时文件写入并替换状态文件成功后，才执行第一条停用。写盘失败即中止，不停用任何规则；此时默认策略可能已经设为阻止，但原始策略已提前保存，可供恢复。

重复连接或上次操作中途退出时，原始默认策略不覆盖，`disabledRules` 采用旧名称与新发现名称的并集，避免遗漏已经停用而不会再次被“已启用”查询找到的规则。每条停用失败都继续尝试后续规则，失败名称收进 `disableFailed` 后再次写盘。失败记录保留历史名称，不等同于每条规则的当前启用状态。

## 断开与崩溃恢复

主动断开先删除本项目 `YuanC-KS-` 前缀规则，再读取状态文件：

1. 对 `disabledRules` 中每个名称在本机持久化存储中精确核对并尝试启用；用户已经删除的规则跳过，不重新创建。
2. 全部尝试后，将三个配置的默认出站策略恢复为连接前保存的值。
3. 恢复成功才删除状态文件。若有启用失败，默认策略仍会尝试恢复，随后报错并保留记录，不能当成全部恢复成功。

客户端启动时发现状态文件，就走相同的恢复流程；无论其中 `applied` 是真还是假，都涵盖连接操作中途崩溃的情况。进程意外退出本身不会立即撤销保护，恢复在客户端再次启动时执行。

旧状态文件没有 `disabledRules` 字段时，判空后只恢复原始默认策略，保持旧版兼容。状态文件不存在时，断开恢复操作仍按既有行为把三个配置的默认出站设为允许；启动恢复入口没有状态文件时仍不执行操作。

如果恢复记录丢失，在默认出站已恢复为允许的前提下，那些停用的允许规则仍会停着，但不会因此阻止正常上网；其他既有阻止规则仍然有效。此时已经无法从丢失的名单自动还原每条规则的启用状态。`run/firewall-audit.json` 可用于检查审计时仍启用的其他允许规则及不可管理规则，但它不是完整停用名单的备份，也不能替代状态文件。不能把“记录丢失”理解为默认策略会自行恢复。

## 组策略与审计

另查有效存储 `ActiveStore` 中已启用、出站、允许、非本项目前缀且名称不在本机持久化存储中的规则。这类规则可能由组策略等来源下发，本机无法按本方案修改，只把名称与程序路径记录到状态文件的 `unmanagedRules`，不尝试停用或删除。

审计文件改为对象，包含三个字段：

- `foreign_allow_rules`：审计当时有效存储中仍启用的非本项目出站允许规则，记录 `Name` 与 `Program`，查询口径与旧审计相同。
- `unmanaged_rules`：来自状态文件的不可管理规则名单；没有状态文件或旧文件缺少该字段时，现场查询上述差集。
- `generated_at`：本次审计生成的世界协调时间，使用 ISO 8601 格式。

组策略规则和停用失败的规则可能仍允许物理网卡直连，不能据此承诺这些机器已完全无泄漏。审计提供界面导出与说明所需信息；本单不修改审计读取方或增加界面提示。状态文件与审计文件的既有路径保持不变。

## Windows 核心网络规则的影响

连接期间，符合筛选条件的 Windows“核心网络”出站允许规则也会停用，包括相关域名解析和第六版互联网协议规则。流量统一经过 `YuanC-TUN` 隧道网卡，由本项目隧道规则放行，是这次方案的设计意图；不能为了恢复直连而另加系统规则豁免。动态地址分配、回环与内核到节点仍由原有本项目规则放行。具体系统版本上的域名解析、双栈及地址更新效果需真机核对。

## 自动检查与既有断言同步

新增测试检查计划类型顺序、记录先于停用、名单并集、持久化存储筛选、单条失败继续记录、恢复顺序、旧文件字段判空、删除范围、审计形状，以及节点切换行为不变。脚本文本检查与构建成功不能证明真实防火墙命令已经执行成功。

按派单方第一次岔路答复，只同步一条与新目标直接冲突的既有断言：改前要求连接脚本不含 `Disable-NetFirewallRule`；改后要求只对本项目前缀执行删除、不执行规则属性修改、停用必须晚于名单写盘，且启用仅出现于恢复脚本。其余既有断言保持原样。

## 真机待验证清单（本单未执行）

- 在 Windows 10 与 Windows 11 的隔离测试机保存连接前规则名称、启用状态及三个配置的默认策略；准备普通应用、系统核心网络、已停用、阻止及入站规则作为对照。
- 连接后核对仅目标允许规则被停用；验证应用经隧道访问、域名解析、双栈及动态地址分配。反复连接并在中途退出，确认记录并集与原始默认策略没有丢失。
- 分别终止隧道内核、移除隧道网卡或使隧道路由失效，抓取物理网卡流量，验证测试应用无绕过隧道的直连；区分本项目允许的节点、回环、动态地址分配通信。对组策略或停用失败造成的例外逐项保留证据，不标成零泄漏通过。
- 主动断开与客户端崩溃后重启，比较恢复后的规则启用状态及默认策略是否与连接前一致；已被用户删除的规则应跳过，未涉及规则不应变化。
- 分别使用旧格式记录、缺失记录、写盘失败与单条停用或启用失败场景，确认兼容、保留记录和错误反馈，核对审计中的不可管理来源。
- 准备几百条符合条件的规则，测量连接停用和断开恢复的实际耗时，并验证超过时限后的恢复路径。本次执行超时从 45 秒调整为 180 秒，实际耗时尚未实测。

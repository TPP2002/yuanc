# Windows 客户端断网保护加固说明

## 原来的缺口与本次修复

以前连接时把三个防火墙配置的默认出站策略设为阻止，但 Windows 的显式允许规则仍然生效。第三方程序安装时创建的允许规则，以及系统自带的“核心网络”允许规则，都可能让流量在隧道内核退出、隧道网卡消失或路由失效后从物理网卡直连。

本次按已批准方案临时停用这些允许规则。连接时的顺序为：先保存三个配置的原始默认策略及启用状态，再依次开启并设为阻止；记录并停用其他允许规则；创建本项目的节点、隧道网卡、回环、动态地址分配、局域网五类放行规则；核对配置档实际生效值，通过后写审计结果。节点与回环放行口径保持不变，动态地址分配与隧道两类规则已收窄（见「动态地址分配规则收窄」「隧道网卡规则按本地地址匹配」两节），节点切换仍只替换本项目的节点规则。分发版另加下节所述的鉴权窄规则。

## 服务重启时保持保护

> 下文既有默认出站阻止、停用第三方放行规则的流程适用于「全部流量」；「仅指定程序」使用本文新增专节的逐程序阻断流程。

原来的缺口：后台服务重启或开机时，运行时创建与控制器初始化都会先恢复上次防火墙记录，撤销默认出站阻止，再鉴权并连接。只有取得会话后才重新套用保护；鉴权服务器不可达时，这个直连窗口可能无限长，违反「隧道断了不静默回落」。

现在先读取期望状态。期望不是 false（包括记录缺失或损坏）、存在恢复记录，且有配对文件或鉴权凭据时，启动不执行 RecoverAsync 或 RemoveAsync，保持默认出站阻止，发布「后台服务已重新启动，断网保护保持，正在恢复连接。」后直接连接。分发版重新向服务器鉴权，自用版读取配对会话；取得会话后先重新套用保护，再启动内核。重复套用不覆盖原始快照，停用规则名单取并集，本项目规则先删后建，沿用既有幂等脚本。

鉴权地址不可达时按既有退避重试，界面显示「重连中」；重试耗尽后转为「需人工处理」，沿用原有提示。服务启动、重连中、需人工处理的全程保护都保持，不恢复直连。用户要上网必须自己点断开，走既有撤防与恢复网络流程；也可点「连接」重新尝试。状态机迁移、退避间隔和次数上限不变。

只有期望明确为断开，或没有配对／鉴权凭据、没有服务器配置时，才走原有恢复网络路径；期望为断开时不自动连接。没有恢复记录时仍按既有流程调用恢复入口（无记录不操作防火墙），再按自动连接条件处理。两层降级恢复只在走恢复路径时发生，保持保护路径不会触发降级放行。

分发版多一条 `YuanC-KS-Auth` 出站允许规则，位于两条节点规则之后、TUN 规则之前，只放行当前后台服务进程到配置的鉴权服务器 IPv4 地址与端口，只使用 TCP。程序取当前进程的完整路径，地址与端口取服务器配置；不放行其他程序，不增加系统 DNS 规则。服务器地址必须是 IPv4 数字地址，不使用域名或 IPv6；HTTPS、配置文件所有者和内核路径校验继续保留。自用配对模式不访问鉴权服务器，不创建这条规则；断开时既有 `YuanC-KS-*` 前缀删除自然覆盖它。

真机待验证项（本单未执行）：

- 连接中结束后台进程，由系统重新拉起服务；期间另开程序持续 ping 公网，应全程无回应，直到隧道重新就绪。
- 把鉴权地址改成不可达的 IPv4 数字地址后重启服务，期间另开程序持续 ping 公网，应全程无回应，直到用户点断开；界面先显示重连中，重试耗尽后显示需人工处理。
- 期望为断开时重启服务，应恢复网络、不自动连接。

## 防火墙配置档被关闭或被策略覆盖

原实现只设默认出站 `Block`，没有设置或核对配置档的 `Enabled`。当配置档为 `Enabled=False` 时，整套防火墙规则不生效，隧道内核停止后可能从物理网卡直连，而界面仍显示保护未撤销。负责人本机 Windows 10 专业版于 2026-10-22 实测三个配置档均为 `False`（本单引用的背景事实，施工方未做真机复测）。域组策略也可能把本地默认出站设置覆盖为允许，不能以本地写入成功代替实际生效。

现在首次连接先记录 Domain、Private、Public 的原 `Enabled` 与默认出站策略，再强制三个配置档 `Enabled=True`、默认出站 `Block`。创建完项目规则（自用六条，分发版另加鉴权窄规则，共七条）后、审计之前，通过 `Get-NetFirewallProfile -PolicyStore ActiveStore` 核实际生效值：必须恰好三条，全部开启且默认出站为阻止。重复连接不覆盖原始快照。仅初始关闭但能够成功开启的配置档可自动修复；强制设置之后仍未满足要求才拒绝连接。组策略覆盖时本机可能无法改变实际值，首次连接仍拒连；已持有保护的重套用路径按下节保持隧道并告警。

首次连接核查失败先保存失败名单及时间，再以固定退出码 `3` 结束；不会继续审计、标记本次安装成功或启动隧道。执行器将它映射为专用异常，控制器在处理失败状态及其提示之后，透出以下原文：

> 系统防火墙已被关闭或被策略覆盖，断网保护无法生效，已拒绝连接。请点击断开，在 Windows 安全中心开启防火墙（或联系管理员解除策略）后重新连接。

此时状态仍为 `NeedsManual`、`ProtectionActive=true`，表示部分安装产生的改动仍需显式恢复，不表示保护已验证有效。用户点击断开走既有恢复流程：记录包含合法 `Enabled` 时，同时还原启用状态和默认出站；旧记录没有此字段时仅恢复默认出站，不替用户决定开关。字段存在但不是 `True`/`False` 时，严格恢复报“防火墙恢复记录无效”；启动降级恢复将该记录判为无效而继续既有流程，`windows_default` 分支只设默认出站 `Allow`，不碰 `Enabled`。服务退出语义、节点切换路径及其他恢复操作保持原样。

新增记录字段：

- 状态文件 `profiles[].Enabled`：连接前启用状态，保存为字符串 `True` 或 `False`。
- 状态文件 `verifyFailed`：本次核查不合格的配置档名称数组；数量不为三条时列入三个应有配置档名称，全部通过时为空数组。
- 状态文件 `verifiedAt`：本次核查的 UTC ISO 8601 时间，成功和失败均记录；旧记录在核查时补齐这两个核查字段。
- 审计对象 `profiles_effective`：审计当时再次读取 `ActiveStore` 的 `Name`、`Enabled`、`DefaultOutboundAction`。核查失败时不会生成本次审计，不能拿之前的审计当作本次成功证据。

真机待验证项（本单均未执行）：

- 在三个配置档均关闭的隔离机器上，验证强制开启后实际值仍关闭或被策略覆盖的场景：连接应被拒绝并出现上述提示，内核不启动，随后点击断开，`Enabled` 应按原记录还原为关闭。若没有策略阻拦且能够自动开启，按上述自动修复行为核对连接和断开恢复，不把初始关闭本身当作拒连条件。
- 正常机器连接后检查 `Get-NetFirewallProfile -PolicyStore ActiveStore`，三档必须全部 `Enabled=True` 且默认出站为 `Block`，审计实际值应一致；断开后启用状态与默认策略应与连接前一致。
- 分别验证组策略将默认出站覆盖为允许、旧记录缺少 `Enabled`、记录中 `Enabled` 非法以及安装中途退出后的恢复，确认拒连或兼容分支、失败记录和用户提示与上文一致。保留原有规则范围、入站规则及服务生命周期的对照证据。

以上是连接时的核查；连接期间的持续巡检现按下节实施。第三方安全软件接管防火墙仍属局限。脚本文本检查、命令替身与自动测试通过不能代替上述真机验证。

## 已持有保护时防火墙失效:保持隧道并告警

负责人 2026-10-22 原则原话：「只要保证使用中,不管什么意外,IP 一直是澳洲宽带就行」，本次拍板为「保持隧道并报警」。如果防火墙已经挡不住直连，再因重新套用失败而停止隧道，会使整机直接使用原网络；因此以下已持有保护的路径遇到防火墙核验失败时，继续执行后续启动隧道，并持续显示红字告警。

「已持有」包括：

- 后台服务重启，保持保护初始化分支发现上次的恢复记录，且存在配对文件或有效鉴权凭据；沿用该记录视为已持有，再连接时适用本规则。
- 本进程已经成功套用过保护，分发版重新鉴权遇到网络失败或限速，进入重连并退避后重新取得会话，再次套用保护。
- 仅指定程序模式沿用相同的判定和处理，重新套用程序阻断规则失败时也保持隧道并告警；它的计划和巡检脚本不变。

首次连接（本进程尚无成功套用记录，也未从保持保护分支继承记录）仍拒连。失败后再次点击连接也不会把部分安装当成验证成功：仍进入需人工处理，显示原异常原因，不启动隧道。主动断开成功撤销保护时，同时清除本进程的成功记录与保持隧道告警。

保持隧道时，巡检状态和主消息显示以下原文，隧道启动成功的常规提示不会覆盖它：

> 断网保护未能重新套用:系统防火墙已被关闭或被策略覆盖,隧道保持但失去断网兜底;请立即在 Windows 安全中心开启防火墙或联系管理员

巡检仍失效时继续显示既有「断网保护可能失效」告警，隧道不停。后续巡检成功、缺失规则完成重建后，清除保持隧道告警，主消息显示「断网保护已重新生效。」；没有其他变动时巡检状态为「正常」。全部流量巡检成功证明当次 `MpsSvc` 正在运行、三档已经重新收紧；仅指定程序模式沿用自身核验条件，不增加默认出站阻断。

剩余窟窿：防火墙失效期间，如果隧道进程崩溃，从崩溃到重连成功前仍可能直连。保持隧道不能替代失效的断网兜底，也不能把负责人原则标成已获所有意外下的保证；根治另见 `SEC-WIN-WFP-KILLSWITCH-1022`，本单不实施 WFP 过滤。

真机待验证项（本单均未执行）：

- 连接中停止 `MpsSvc` 后重启后台服务：隧道应启动，界面显示上述红字告警。
- 停止 `MpsSvc` 后首次连接：应拒绝连接，隧道不启动，再点连接仍拒绝。
- 保持隧道告警期间恢复 `MpsSvc`：正常空闲条件下 60 秒内应出现「断网保护已重新生效。」；实际时限仍须真机验证，命令耗时及串行队列可能推迟巡检。

## 局域网放行

全部流量模式增加 `YuanC-KS-Lan`：出站、`Allow`、`RemoteAddress=["LocalSubnet"]`，不限程序、服务、协议、端口或本地地址。计划写法为 `new AddRule(Prefix + "Lan", "Outbound", "Allow", RemoteAddress: ["LocalSubnet"])`，既有脚本分支生成 `New-NetFirewallRule -Name 'YuanC-KS-Lan'`，带 `-RemoteAddress @('LocalSubnet')`，关键字原样交给 Windows，不展开地址。

规则放在 DHCP 规则之后、配置档核验之前，巡检预期规则末尾也加入它。顺序为 Node-Tcp、Node-Udp、可选 Auth、Tun、Loopback、Dhcp、Lan；自用六条，邀请码七条。缺失时沿用既有巡检重建，主动断开时随 `YuanC-KS-*` 前缀删除。仅指定程序模式没有默认出站阻断，不增加此规则。

这条规则允许打印机、NAS、投屏设备和路由器管理页等局域网目标：目的地址在局域网内，包不出公网，因此不会直接放行公网目标。唯一例外是局域网内另有代理设备，用户手动把流量指向它，再由它转发到公网；这属于用户自行配置的行为，不是本规则直接允许公网访问。

真机待验证项（本单均未执行）：连接期间能够打印、访问路由器管理页与 NAS；断开后 `YuanC-KS-Lan` 随本项目前缀删除；公网目标仍只能经隧道访问。须结合抓包核对目标地址和实际路径，单测与脚本文本检查不能替代真机结果。

## 连接期间巡检

后台服务在断网保护保持、状态为已连接或重连中时安排巡检，首次等待 60 秒，每轮完成后再等待 60 秒。重复进入这些状态不重复安排；退出这两个状态或保护关闭后不再续排。沿用控制器的串行锁与生命周期，主动断开使旧回调作废，清空界面巡检状态。巡检复用现有隐藏窗口的 PowerShell 执行器与防火墙串行锁，单次超时 180 秒；命令耗时及串行队列可能推迟实际执行时间。

每轮按以下顺序执行：

1. 读取 `ActiveStore` 的配置档，对未开启或默认出站不是 `Block` 的配置档重新开启并收紧，记录名称。
2. 仅在恢复状态文件存在时，停用 `PersistentStore` 中所有当前已启用的第三方出站允许规则（含被程序同名重建或重新启用的），仍排除 `YuanC-KS-*`。名字并入 `disabledRules`，先原子写盘再逐条停用；失败名称加入 `disableFailed` 后再次写盘。状态文件不存在时不操作第三方规则，也不创建恢复记录。本轮实际成功停用的名字计入 `newly_disabled`，重新启用的同名规则会再次出现在这里。
3. 按名字到 `ActiveStore` 核对本项目规则：不存在、同名数量不是一条、被停用、动作不是 Allow、方向不是 Outbound、或程序 / 服务 / 本地与远端地址 / 协议 / 端口与套用时记录（状态文件 `rules`）不一致都算缺失，进入 `missing_rules`。自用六条、邀请码七条（另含 `YuanC-KS-Auth`），两者都包含末尾的 `YuanC-KS-Lan`。
4. 检查 `MpsSvc` 是否运行；没有运行以退出码 `3` 报告。
5. 再读 `ActiveStore` 核对配置档，仍未开启或默认出站不是 `Block`（含配置档不完整）时，在已有状态文件中记录 `verifyFailed`，以退出码 `3` 报告。
6. 成功时最后一行输出紧凑结果，含重新收紧的配置档、新停用的规则及缺失规则；操作或解析失败按巡检失败处理。

巡检脚本本身只收紧配置、停用规则及写恢复记录，不创建、删除、启用规则，不改入站。缺失本项目规则时，控制器在有会话的前提下调用既有幂等安装恢复项目规则，不撤销断网保护；没有会话时跳过重建并提示下一轮重试。

每条允许规则创建成功后，将期望按名字覆盖同名项记入状态文件的 `rules` 数组，字段为 `Name`、`Program`、`Service`、`LocalAddress`、`RemoteAddress`、`Protocol`、`LocalPort`、`RemotePort`；地址为数组，未指定的字段保留为空值。套用结束随既有状态写盘；切换节点只加载并写回已存在的状态文件，更新两条节点规则的期望，没有状态文件时不新建。

程序、服务、协议和端口不区分大小写比较，未指定时实际值须为 `Any` 或空；地址两侧分别去空白、转小写、去重、排序后比较，未指定时实际值须为 `Any`。状态文件来自旧版本（无 `rules`）时只核存在 / 启用 / 动作 / 方向，下次重新连接后才有内容核对。

三种正常结果及界面文字：

| 结果 | 界面文字 |
|---|---|
| 没有发现变动 | `断网保护巡检:正常` |
| 重新收紧配置档或停用新规则 | `断网保护巡检:已重新收紧 n 条规则`，数量为配置档与新停用规则之和 |
| 本项目规则缺失且重建成功 | `断网保护巡检:已重建 n 条本项目规则`，数量为发现的缺失规则数；优先显示此结果 |

退出码 `3` 表示服务未运行或实际生效配置仍不符合要求，界面红字显示「断网保护巡检:系统防火墙已被关闭或被策略覆盖,断网保护可能失效,请立即在 Windows 安全中心开启防火墙或联系管理员」，主消息同步显示该告警。其他操作异常显示「断网保护巡检:巡检失败,下一轮重试」。两种异常都继续安排下一轮。

**任何出口核验或巡检结果都不自动断开隧道，也不自动撤销断网保护。** 主动断开会进入恢复普通网络的路径；若检测到问题就自动断开，反而可能造成真实直连泄漏。告警用于通知用户处理，不能把保持保护标志理解成系统防火墙始终有效。组策略与第三方接管仍可能影响实际保护，定期检查不能证明所有时刻零泄漏。

出口 IP 核验也只在后台服务进行：连上后等待 3 秒，经隧道请求 `https://1.1.1.1/cdn-cgi/trace`，不解析域名、不跟随跳转、不使用系统代理或 Cookie，不附带设备信息，不记录响应正文或地址日志。单次超时 5 秒，只有成功响应中的有效 `ip=` 地址才参与比较。与节点地址相同显示「当前出口 IP:地址(与澳洲节点一致)」；不同显示「⚠ 当前出口 IP:地址,与澳洲节点不一致,请联系管理员」，并提示保护保持、未自动断开。没有结果每 5 秒重试，累计 5 次仍失败显示「当前出口 IP:无法核验(隧道内暂无回应)」。每次终局后等待 5 分钟重新核验；离开已连接状态清回待检测，核验期间显示「当前出口 IP:核验中…」。比较结果只证明取得的地址是否与配置节点一致，不能独立证明地理位置或家庭宽带属性。

真机待验证项（本单全部未执行）：

- 出口核验一致、不一致、无法核验三种界面分别验证；后两种情况下隧道不断、保护不撤，五分钟后能够再次核验。
- 连接后新建一条任意程序的出站允许规则，正常空闲条件下 60 秒内应被停用，名称记入 `disabledRules`；随后主动断开可按记录恢复。
- 手动把某配置档默认出站改回 `Allow`，正常空闲条件下 60 秒内应被改回 `Block`，界面显示「已重新收紧」。
- 停掉 `MpsSvc` 服务，界面应出现上述红字提示，隧道保持运行且没有自动撤防；恢复服务后下一轮仍可巡检。

## 停用范围与先记录的原因

只选本机持久化存储 `PersistentStore` 中当前已启用、出站、允许的规则，排除名称以 `YuanC-KS-` 开头的规则。不会停用入站规则或阻止规则，也不会把连接前已经停用的规则加入恢复名单。

对其他程序和系统规则只执行停用、启用，不删除规则，不修改程序、端口、地址等属性。删除后无法可靠重建原始条件，而保留规则只切换启用状态才能按名单恢复。

必须**先记录，再停用**：把名称列表写入 `run/killswitch-state.json` 的 `disabledRules` 数组，经临时文件写入并替换状态文件成功后，才执行第一条停用。写盘失败即中止，不停用任何规则；此时默认策略可能已经设为阻止，但原始策略已提前保存，可供恢复。

重复连接或上次操作中途退出时，原始默认策略不覆盖，`disabledRules` 采用旧名称与新发现名称的并集，避免遗漏已经停用而不会再次被“已启用”查询找到的规则。每条停用失败都继续尝试后续规则，失败名称收进 `disableFailed` 后再次写盘。失败记录保留历史名称，不等同于每条规则的当前启用状态。

巡检每轮重新停用所有已启用的第三方允许规则，恢复名单只做并集记录，不做排除条件。

## 断开与崩溃恢复

主动断开先删除本项目 `YuanC-KS-` 前缀规则，再读取状态文件：

1. 对 `disabledRules` 中每个名称在本机持久化存储中精确核对并尝试启用；用户已经删除的规则跳过，不重新创建。
2. 全部尝试后，将三个配置的默认出站策略恢复为连接前保存的值。
3. 恢复成功才删除状态文件。若有启用失败，默认策略仍会尝试恢复，随后报错并保留记录，不能当成全部恢复成功。

客户端启动时按上节的期望状态与配对／凭据分路；只有进入恢复路径时，才对状态文件走相同的恢复流程，失败后再按下节降级处理。无论其中 `applied` 是真还是假，都涵盖连接操作中途崩溃的情况。进程意外退出本身不会立即撤销保护；满足保持条件的再次启动也不会撤防。

旧状态文件没有 `disabledRules` 字段时，判空后只恢复原始默认策略，保持旧版兼容。状态文件不存在时，断开恢复操作仍按既有行为把三个配置的默认出站设为允许；启动恢复入口没有状态文件时仍不执行操作。

如果恢复记录丢失，在默认出站已恢复为允许的前提下，那些停用的允许规则仍会停着，但不会因此阻止正常上网；其他既有阻止规则仍然有效。此时已经无法从丢失的名单自动还原每条规则的启用状态。`run/firewall-audit.json` 可用于检查审计时仍启用的其他允许规则及不可管理规则，但它不是完整停用名单的备份，也不能替代状态文件。不能把“记录丢失”理解为默认策略会自行恢复。

## 启动恢复失败的降级处理

后台服务启动仅在进入恢复路径时采用两层恢复，保持保护路径跳过此流程。第一层仍按原记录严格恢复，既有删除项目规则、启用名单规则和恢复默认出站的脚本不变；成功则清除本进程的降级提示。第一层退出失败且活动状态文件仍在，才运行第二层：

1. 在状态文件同目录，按名字倒序保留最新四份 `killswitch-state.failed-*.json`，删除更旧的归档，再用 `Copy-Item` 复制活动记录为 `killswitch-state.failed-<UTC yyyyMMddTHHmmssZ>.json`。加上本次归档最多五份。归档是复制，活动记录此时不删除；复制失败即中止，不修改防火墙设置。
2. 宽松解析活动记录，解析失败按无有效记录处理。三个配置名称及其默认出站值全部合法时，逐条恢复记录值；否则将 Domain、Private、Public 的默认出站设为 Windows 系统默认 `Allow`。这避免损坏记录使默认出站一直停留在阻止状态；它不能还原损坏记录中已经无法读取的自定义策略。
3. 尽力启用 `disabledRules` 名单中本机持久化存储的对应出站规则，单条启用失败只收集名称，继续后续恢复。不停用规则、不新建规则、不改入站规则；删除仍只针对 `YuanC-KS-*` 项目规则。默认出站为允许时，名单内个别允许规则未能启用不会因此阻止普通上网，但其他既有阻止规则仍然有效。
4. 将恢复结果经临时文件写入并替换 `killswitch-recovery.json`，最后一步才删除活动状态文件 `killswitch-state.json`，然后返回成功。恢复配置、写证据或收尾失败仍报错；活动记录未成功删除时会保留，供初始化再次尝试及下次开机重试。

降级成功会通过既有界面消息提示，并按原有期望状态和本地配置照常自动连接，不要求用户先确认。提示在本进程内保留，后续没有活动记录的启动恢复调用也会返回该提示；新的严格恢复成功后清除。自动连接产生的连接结果与降级提示一起显示，不能把提示理解为真实出口已经验证。

两层都失败时，运行时创建不再因该恢复异常退出，由控制器初始化再试；仍失败才进入“需人工处理”，显示“启动时未能恢复上次的断网保护设置，恢复记录已保留；请联系管理员处理后重新启动后台服务。”后台服务保持运行，界面能够查询原因，不再因同一恢复异常反复重启。其他异常的服务退出语义保持不变。没有活动记录时不执行恢复脚本。

主动断开仍保持“不把部分成功报成功”：名单规则恢复失败就报错并保留记录，不走降级。只有启动路径允许这项例外，以免客户因损坏的历史记录长期无法上网或连界面都无法使用；不改变连接期间的断网保护和重连策略。

管理员应检查 `%ProgramData%\YuanC\run` 下的以下证据，先对照时间与归档文件名，再决定如何恢复未启用的规则：

- `killswitch-state.json`：当前仍待恢复的活动记录；存在时不要直接删除来掩盖恢复失败。降级完成后自动连接可能产生新的活动记录，应结合归档与时间判断。
- `killswitch-state.failed-*.json`：降级前的原始记录副本，最多五份；可核对原默认策略和 `disabledRules`。损坏内容也按原样保留。
- `killswitch-recovery.json`：`at` 为 UTC 时间，`archived` 指向归档文件名，`record_valid` 表示配置记录是否合法，`profiles_applied` 为 `recorded` 或 `windows_default`，`rules_not_enabled` 列出未能启用的规则。中途失败可能未写入新结果，因此须核对时间，不能仅凭旧文件判成功。
- `killswitch-recovery.log`：每次脚本非零退出追加 UTC 时间、`restore` 或 `fallback` 阶段及退出码。当前命令结果不携带标准错误文本；日志追加失败不阻断恢复。`service.log` 会记录运行时创建阶段的降级提示。界面导出诊断仍只导出原来的防火墙审计文件，不包含这些恢复证据。

本节真机待验证项（本单未执行）：在隔离的 Windows 测试机分别伪造一份损坏记录、准备一条启用不了的名单规则，各复现一次；核对默认出站、复制归档、失败名单、界面提示和照常自动连接。另验证归档复制失败及归档成功后恢复配置或写证据失败：活动记录必须保留，连续失败进入需人工处理而服务保持运行，下次开机仍会重试；连续归档后最多五份。与修改前的入站和非项目规则清单比较，确认未越界。自动脚本文本检查和命令替身不能代替这些真机验证。

## 组策略与审计

另查有效存储 `ActiveStore` 中已启用、出站、允许、非本项目前缀且名称不在本机持久化存储中的规则。这类规则可能由组策略等来源下发，本机无法按本方案修改，只把名称与程序路径记录到状态文件的 `unmanagedRules`，不尝试停用或删除。

审计文件为对象，保留原有三个字段，并新增实际配置档值：

- `foreign_allow_rules`：审计当时有效存储中仍启用的非本项目出站允许规则，记录 `Name` 与 `Program`，查询口径与旧审计相同。
- `unmanaged_rules`：来自状态文件的不可管理规则名单；没有状态文件或旧文件缺少该字段时，现场查询上述差集。
- `generated_at`：本次审计生成的世界协调时间，使用 ISO 8601 格式。
- `profiles_effective`：实际生效的配置档值，详见上节“防火墙配置档被关闭或被策略覆盖”。

组策略规则和停用失败的规则可能仍允许物理网卡直连，不能据此承诺这些机器已完全无泄漏。审计提供界面导出与说明所需信息；本单不修改审计读取方或增加界面提示。状态文件与审计文件的既有路径保持不变。

## Windows 核心网络规则的影响

连接期间，符合筛选条件的 Windows“核心网络”出站允许规则也会停用，包括相关域名解析和第六版互联网协议规则。流量统一经过 `YuanC-TUN` 隧道网卡，由本项目隧道规则放行，是这次方案的设计意图；不能为了恢复直连而另加系统规则豁免。动态地址分配、回环与内核到节点仍由原有本项目规则放行。具体系统版本上的域名解析、双栈及地址更新效果需真机核对。

## 动态地址分配规则收窄

原规则只限 UDP 本地 68 端口到远端 67 端口，不限程序与远端地址：能绑定本地 UDP 68 的任何进程，都可以往公网任意地址的 67 端口发包。现在 `YuanC-KS-Dhcp` 只放行 `svchost.exe`（系统目录下）里的 `Dhcp` 服务，远端只到广播地址 `255.255.255.255` 与本地子网（防火墙关键字 `LocalSubnet`，原样写入，不展开），协议与端口仍为 UDP 68 到 67。规则总数与顺序不变。

## 隧道网卡规则按本地地址匹配

原规则按网卡别名 `YuanC-TUN` 建立，但状态机先套用防火墙再启动隧道内核，此时 wintun 网卡尚不存在，这种情况下系统的行为没有真机记录。现在 `YuanC-KS-Tun` 按本地源地址 `172.19.0.1` 匹配，不再写网卡别名，网卡出现之前就能建成；强主机模型下该源地址只会从隧道网卡发出。IPv6 的隧道地址 `fdfe:dcba:9876::1` 不放行，与路由里阻止 IPv6 一致。计划函数仍保留网卡名参数与非空校验，隧道传输仍用它给网卡命名，只是规则不再使用。测试会核对渲染出的隧道地址与防火墙常量一致。

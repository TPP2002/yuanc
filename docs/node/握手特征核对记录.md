# 主通道握手特征核对记录(内核 1.10.7 对照当前 Chrome)

> 看板卡 SEC-TUNNEL-UTLS-FP-1022(来源:对抗审查 C-L4)。核对日 2026-10-24,本机完成,不依赖澳洲真机。

## 结论

**对不上。** 客户端配置 `utls.fingerprint = "chrome"`,内核钉在 sing-box 1.10.7(`winclient/third_party/manifest.json`),它发出的 TLS 首包(ClientHello)停留在 Chrome 131 之前的样子;本机 Chrome 155 的首包多了抗量子密钥交换等几项,长度差三倍多。两边 JA4 不同:

| 来源 | JA4 | 首包长度 |
|---|---|---|
| sing-box 1.10.7,utls=chrome(VLESS+Reality 出站) | `t13d1516h2_8daaf6152771_02713d6af862` | 564 字节 |
| Chrome 155.0.8059.85(本机,无头模式) | `t13d1517h2_8daaf6152771_cb7bf5808d99` | 1984 字节 |

密码套件一段(JA4 中段)完全一致,差异全在扩展与参数:

| 项 | 内核 1.10.7 | Chrome 155 |
|---|---|---|
| 支持的密钥交换组 | X25519、P-256、P-384 | **X25519MLKEM768(0x11ec)**、X25519、P-256、P-384 |
| 首包携带的密钥份额 | 只有 X25519(32 字节) | X25519MLKEM768(1216 字节)+ X25519 |
| 应用层设置扩展(ALPS)编号 | 旧编号 0x4469 | 新编号 0x44cd |
| 签名算法 | 8 项传统算法 | 前面多 0x0904/0x0905/0x0906 三项(ML-DSA)及一个占位值 |
| 其他扩展 | — | 多一项 0xca34(未查到公开名称) |
| 扩展数(去掉占位值) | 16 | 17 |

影响:主通道每次握手都带着「旧版 Chrome」的特征,和 2026 年真实 Chrome 流量的分布不一致;首包长度差异尤其明显。功能上不影响连通。

## 核对方法(可复现)

全部在 127.0.0.1 上完成,不连外网:

1. 本机起一个只收首包的监听口;
2. 用 sing-box 1.10.7 跑一份最小配置:本地 mixed 入站 + 与产品同参数的 VLESS+Reality 出站(`utls` chrome、`flow xtls-rprx-vision`),服务端地址指向监听口,经 mixed 入站发一次请求触发握手;
3. 用本机 Chrome 无头模式、临时用户目录(不碰本机浏览器资料),把同一个 SNI 解析到监听口并访问;
4. 解析两份首包,按 JA4 规则(去掉占位值、密码套件与扩展排序、扩展段去掉 SNI 与 ALPN、签名算法保持原序)算指纹并逐项对比。

脚本放在 `build/utls-check/capture.py`(`build/` 不入库),经调度台单 `tk-691e3ddbcdea9bf71f1b` 跑过。后续升级内核的卡把它收进仓库当回归检查(见下)。

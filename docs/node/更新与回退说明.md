# 节点更新与回退

## 首次准备

先由发布维护人员生成签名密钥，将公钥写入节点程序，再安装初始可信版本。默认空公钥不接受任何升级包。
私钥留在维护人员的仓库外安全目录，不传到节点。节点只保存公钥。

首次安装前准备好 Linux sing-box，不必把默认 `proxy.binary` 改成系统路径。
默认 `/opt/exitnode/current/bin/sing-box` 尚不存在时，安装器依次从 `/usr/bin/sing-box`、`/usr/local/bin/sing-box` 寻找内核；都找不到则报“未找到 sing-box”，不会自动下载。
`exitnode init` 把运行中的 Python 包、模板及找到的内核复制到 `/opt/exitnode/releases/<版本>/`，建立 `current` 链接。代理服务仍按配置的路径运行，默认路径随版本切换。
相同版本的文件和清单哈希都一致时复用，内容不同会拒绝覆盖。重复安装不重新执行已完成步骤的系统命令。

配置的默认内核路径和服务模板默认路径均为 `/opt/exitnode/current/bin/sing-box`。
显式设置的 `proxy.binary` 仍是内核覆盖路径；需要随整包更新内核的节点应使用默认路径，维护人员应同时核对已有代理服务定义的启动路径。
`updater.releases_dir` 指的是布局根目录（默认 `/opt/exitnode`），其下包含 `releases` 和 `current`。

## 怎样升级

维护人员经管理隧道把升级包及同名 `.sig` 文件复制到节点的临时推包目录，勿放入更新器自己管理的 `incoming` 目录。

```sh
exitnode upgrade --file /tmp/exitnode-0.2.0.tar.gz --check
exitnode upgrade --file /tmp/exitnode-0.2.0.tar.gz
```

签名另存他处时用 `--signature /路径/签名`。只查模式也会验证签名、所有文件、配置兼容和版本下限；需要新安装目录时还检查可用空间，但不安装、不切换。

### 版本只升不降

默认拒绝低于当前版本或低于历史最高已装版本的包：签名只证明包是发布者发的，不证明它是新的。
确需降级回退时，维护人员核对风险后显式加 `--allow-downgrade`；只查模式也遵守同一版本限制。
最高版本记录保存在 `node.data_dir` 下的 `updater/highest.json`，默认位置为 `/var/lib/exitnode/updater/highest.json`，权限为 `0600`。
每次安装或切换通过健康检查并记入成功历史后，原子保存「原记录、切换前版本、新版本」三者中的最高值，语义是只增不减。
因此允许降级不会降低后续升级的版本下限，救援重装切回出厂版本也不会清除此记录。
记录缺失、内容损坏或版本号非法时视为没有记录，下限退回当前版本，避免坏文件阻断更新。

使用 GitHub Releases 时配置 `updater.source = "github"` 与 `github_repo = "owner/repo"`，然后运行 `exitnode upgrade`。
私有仓令牌仅保存到 `/var/lib/exitnode/secrets/github-token`（0600）；请求失败不会显示请求地址、响应体或令牌。
令牌只经标准输入交给下载程序，不出现在命令行参数里，节点本机的进程列表看不到它。
发布源标签与包内版本必须一致，不一致时拒绝安装且不写版本目录。
`source = "none"` 时取包升级必须指定本地包；下文的 `--switch` 不需要发布源或网络。本单不设置定时更新。

`node.config_version` 缺省为 1，必须是正整数。升级包要求的最低配置格式版本更高时，先按发布说明升级配置；不要只改数字绕过兼容检查。
包中最低配置版本缺失或非法会拒收。程序版本按 PEP 440 比较，与当前版本相同（包括等价写法）时拒绝重复安装。

## 失败后机器会怎样

签名、哈希、兼容或空间检查不通过时，不写入新版本目录，清掉本次取包副本，继续使用原程序。
空间至少应有解压文件总大小的两倍加 50 MiB。维护人员推送的原包不删除。

检查通过后先写独立暂存目录，完成校验后再原子切换 `current`。
只重新启动本项目的代理和管理服务，再重新加载服务定义。检查通过才记录成功。
`exitnode-admin.service` 已是客户端包只读托管服务，正式入口为 `admin serve`；旧单元使用的 `--placeholder admin` 也运行同一服务，不再打印占位错误退出。更新器自身逻辑未改。托管内容、发布步骤及新增健康检查层见 [客户端包托管说明](客户端包托管说明.md)。
健康检查使用新程序的 `check --json`，要求“隧道服务”通过，默认最多 120 秒、每 5 秒检查一次；此结果不等于真实外网出口或客户实机验收。

### 健康检查的稳定窗

隧道服务一启动就会显示“运行中”，跑几秒才崩的新版若只看第一次结果会被误判成功，所以健康检查分两段：

1. **第一段**（不变）：每 5 秒以内跑一次新程序的 `check --json`，直到“隧道服务”层通过；超过 `updater.health_timeout_sec` 仍未通过即判失败，第二段不跑。
2. **第二段（稳定窗）**：从第一次通过那一刻起，再观察 `updater.health_stable_sec` 秒（默认 30）。先记下隧道服务的重启次数作为基线，然后每轮按顺序检查四项：
   - `systemctl is-active exitnode-proxy.service` 退出码为 0（服务仍在运行）；
   - `systemctl show exitnode-proxy.service -p NRestarts --value` 读到的重启次数与基线相同；
   - 主通道端口（`proxy.reality_port`，默认 443）与备用通道端口（`proxy.hy2_port`）仍在监听，判定口径与看门狗的监听检查一致（`ss -ltnH` / `ss -lunH`）；
   - 最后一条仍是 `check --json`，“隧道服务”层通过。

   四项都过且已满稳定窗才算健康；否则等待最多 5 秒进入下一轮。稳定窗内任何一轮任何一项失败立即判不健康、走回退，不重试。
   读不到重启次数（命令失败或输出不是数字）、监听信息无法读取（如缺少 `ss`）都记为“未知”，**未知不算失败**，只有明确的失败才会触发回退。

总耗时上限为 `health_timeout_sec + health_stable_sec`（默认 150 秒），每条检查命令的等待时间不超过所在段剩余时间与 30 秒的较小者。
`updater.health_stable_sec = 0` 时关闭稳定窗，行为与以前完全一致，不发出上述额外命令。

新版启动或健康检查失败会切回旧目录、重启本项目服务，并在失败版本旁写 `.bad` 标记。
历史保存在数据目录的 `updater/history.jsonl`。恢复服务本身失败会明确提示人工处理并保留恢复记录。

被回退或救援重装后，再推同一个完整的新版本，只要它不是当前版本、没有失败标记、满足版本下限且文件清单与升级包完全一致，就直接切换并做健康检查，不再当成重复安装，也不重新解包或覆盖已有目录。
包内容与已装目录不一致会拒绝；目录残缺或校验失败也会拒绝，不自动删除或覆盖。已有失败标记的版本仍拒绝使用，不能用允许降级选项绕过。

取包升级断网返回 3，不改文件，稍后重试；显式切换已装版本无需网络。已有更新任务返回 4，不等待。
遗留锁只有超过两小时且原进程不存在时才自动接管；锁写于本次开机之前（锁内时间早于“当前时间减开机时长”）时视为陈旧，直接接管。不应随意删除运行中的锁。
更新进程被杀后，开机收尾单元或下次更新会先按下节收尾未完成的更新，再清理 `incoming` 和暂存目录。
安装和更新入口会检查悬空链接，按版本顺序选择最新、没有失败标记且清单哈希完整的目录恢复。
取包升级断网时零文件变更优先，清理与恢复延至下一次在线调用；显式切换仍按原顺序加锁、恢复未完成事务并清理暂存文件。
另有独立本地救援单元，不依赖联网或更新器；详见 [救援单元说明](救援单元说明.md)。

### 断电或被杀后的开机收尾

更新过程中会在数据目录写 `updater/pending.json`（未完成更新记录），其中 `stage` 字段记录走到哪一步：

- `staged`：新版本目录已就位，`current` 链接还没切换；
- `switched`：链接已切到新版本，正在重启服务或等待健康检查。

没有 `stage` 字段的旧记录保守按 `switched` 处理；`stage` 是其他值按记录损坏处理，提示联系维护人员。

收尾时按 `current` 链接的实际指向分四种情况：

1. `stage` 为 `staged` 且链接仍指向旧版本：切换从未发生，删除没验证过的新版本目录（含同名暂存目录），**不标坏**，历史记一行 `aborted`，删除记录，不重启服务；之后可以重新推同一个版本。
2. 链接已指向新版本（不论 `stage`）：服务已由 systemd 开机按链接拉起，不再重启，直接现场做健康检查（含稳定窗）。通过则转正：历史记 `ok`、删除记录、更新最高版本记录；不通过则切回旧版本、新版本标坏、历史记 `rolled_back`、删除记录。
3. `stage` 为 `switched` 但链接已指回旧版本：新版本仍没验证过，按原逻辑标坏、记 `rolled_back`、删除记录。
4. 链接两者都不是，或读不到：按记录损坏处理，不做任何改动，提示联系维护人员。

安装时会写入并启用开机收尾单元 `exitnode-recover.service`（只 `enable`，不立即运行）。它排在网络与隧道服务之后，每次开机跑一次 `exitnode upgrade --recover`。
`--recover` 只收尾未完成的更新，**不探测网络、不下载升级包**，断网也能完成；没有未完成记录时只打印“没有未完成的更新。”并照常检查悬空链接、清理暂存。
`--recover` 不能与 `--file`、`--signature`、`--switch`、`--check`、`--allow-downgrade` 同时使用。已有更新任务在跑时返回 4。
断电重启后，旧锁写于本次开机之前，按上面的开机规则视为陈旧并接管，不必等两小时。读不到开机时长时不启用这条规则，仍按两小时加进程存活判断。

## 手动回退与目录保留

先停止人工发起新的更新，确认没有正在运行的更新任务，再选择清单完整且没有 `.bad` 的旧版本。
首选更新器切换（把示例版本换成实际版本）：

```sh
exitnode upgrade --switch 0.1.0 --allow-downgrade
```

此命令只使用已经安装的真实版本目录，不下载升级包、不探测网络，未配置发布源也能使用。
切换后会重启本项目服务并做健康检查；失败自动切回切换前版本，并给失败目标标坏。
可先追加 `--check` 只校验目标与版本下限，显示“未执行”，不切换、不重启服务。
`--switch` 不能与 `--file` 或 `--signature` 同时使用；已是当前版本、未安装、目录残缺或有失败标记时均拒绝。

下面的手工步骤仅作为**更新器本身坏了时的兜底**，不具备更新器的自动健康回退保护。维护人员核对版本后执行：

```sh
ln -s /opt/exitnode/releases/0.1.0 /opt/exitnode/current.manual
mv -Tf /opt/exitnode/current.manual /opt/exitnode/current
systemctl restart exitnode-proxy.service exitnode-admin.service
systemctl daemon-reload
PYTHONPATH=/opt/exitnode/current python3 -m exitnode check --json
```

同时核对代理服务及配置使用 `current/bin/sing-box`，否则显式覆盖的内核路径不随链接切换。
不要盲目移除失败标记重新安装同一版本；先查失败原因，修复后发布新版本。

`rollback`、`uninstall` 以及 `uninstall --purge` 都保留整个版本目录。`--purge` 只清除凭据，程序目录不是凭据。
这些命令同样保留 `/opt/exitnode-rescue/`，包括独立救援代码与出厂包；普通升级也不覆盖它。救援代码只通过明确执行 `exitnode rescue refresh` 更新。
不要删除 `current` 指向的版本，也不要删除未完成更新记录依赖的旧版本。确认运行稳定、无更新任务后，维护人员才能清理已不用的历史版本；保留至少一个可回退版本。

## 真机待验证项

本次自动化测试使用内存模拟主机，以下项目尚未在真实节点验证，不能据此宣称部署或实机验收通过：

- 在隔离的 Debian 节点安装和切换版本，确认真实 `systemctl` 重启代理与管理服务，新版本的 `check --json` 健康检查确实执行；人为制造健康检查失败，确认切回原版本、标坏目标、记录回退并清除待完成记录。
- 断网且不配置发布源时执行显式切换及只查模式，确认前者可完成健康检查、后者不切换或重启；确认最高版本记录权限为 `0600`，降级后仍保留较高版本作为后续下限。
- 使用受控的 GitHub 测试发布源，分别验证标签与包内版本相同、不相同的情况；不相同时应拒绝安装且版本目录保持不变。真实发布源下载、令牌访问及标签核对尚待验证，不以模拟响应代替。
- 升级等待健康检查时直接拔电重启，开机后确认 `exitnode-recover.service` 已运行、`pending.json` 消失，且 `history.jsonl` 多一行 `ok`、`aborted` 或 `rolled_back`（视拔电时机而定）；同时确认遗留的更新锁被接管、随后的升级不再返回 4。
- 推一个启动后几秒就崩溃的测试版本，确认稳定窗内能发现（服务不再运行或重启次数增加），自动切回旧版并标坏；确认真实 `systemctl show ... NRestarts` 与 `ss` 输出能被正确解析。

# 节点看门狗维护说明

它负责在节点异常时自动检查和有限恢复。软件测试使用模拟主机，不代表已经在澳洲设备上验过拔网线、断电或硬件死机。

## 每分钟检查什么

安装成功后，开机等待 90 秒开始第一轮，此后每分钟检查一次：

1. 网卡是否启用、是否取得地址和默认路由。
2. 能否连接至少一个配置中的外网探测目标。
3. 隧道服务是否正在运行、当前配置能否通过内核检查。
4. 本机两个入口是否监听：主入口 443、备用入口取配置中的端口。缺少监听查询工具时记录“未知”，不把它当成故障。
5. 前面没有失败时才查询公网地址；查询失败只等待外网恢复，不因此重启服务或整机。

全部检查通过后，状态为“正常”，清零连续失败次数，记下最近成功时间。当前隧道配置与保留副本不同才更新副本。设备增删或放行名单同步发布成功时也会同步更新该副本，所以副本不会停在吊销之前。副本与状态文件权限均为仅管理员可读写。成功恢复不会清掉重启、回滚的频率限制。

## 什么情况会重启服务

第一次发现失败，在同一轮里立即再查一次，最多一次。仍失败时记一次失败；第二、第三次失败只记录，第四次才考虑恢复动作。重复手动执行不能把一分钟内的失败当成多分钟。

只有隧道服务或本机入口异常才重启本项目的隧道服务。网线、路由器或宽带异常不重启服务。

普通服务重启每小时最多三次。连续重启之间默认等待 60、120、240 秒，等待时间最多 300 秒。三次仍无效，立即尝试恢复上次可用配置；回滚前先检查暂存副本，检查失败不替换当前配置。没有副本则跳过回滚，转为“需人工处理”。

回滚前按设备登记表剔除副本里已吊销或不在名单上的用户记录，再交给内核检查；登记表损坏则不回滚，转为“需人工处理”。登记表不存在时按空名单处理。恢复成功后提示“已剔除 N 条不在登记表上的用户记录”：剔除 N 条用户记录（同一台设备在主通道与备用通道各算一条），不显示设备标识或凭据。

**回滚与普通服务重启使用独立额度。** 回滚自带的一次服务重启不占用普通重启的三次额度；回滚六小时内最多一次。回滚失败或下一轮仍未恢复，会提示人工检查，不继续反复回滚。动作记录分别叫 `restart_service` 和 `rollback_config`，便于追查。

## 什么情况会重启整机

必须同时满足：已经进入“需人工处理”、连续异常至少 30 分钟、最近六小时没有尝试过整机重启，并且配置允许整机重启。网卡或默认路由异常也计算连续失联时间。只有公网地址查询失败不会触发整机重启。

重启前先保存时间；即使命令失败，也不会立刻重复尝试。状态文件损坏时会重建并记录，同时保守冷却恢复额度，避免把丢失的历史当成新的重启机会。机器恢复正常后连续失败时间重新计算。

这不能修复断电、坏硬盘、坏电源或运营商故障。需要人工时，查看原因并检查网线、路由器、宽带、服务权限和配置。

## 查看状态

在节点上使用：

```sh
exitnode status
exitnode status --json
exitnode watchdog status
exitnode check
```

总状态会显示“正常”“重连中”或“需人工处理”。机器可读结果包含最近成功时间、连续失败次数和最近动作；还没有运行记录时看门狗字段为空。详细记录位于配置的数据目录下 `watchdog/state.json`，只保留最近 50 条动作。频率记录另行保存，不受这 50 条限制影响。

检查命令中的“看门狗”要求定时器正在运行，并且最近 10 分钟内有状态更新，且检查任务没有被 systemd 启动频率限制拦下；这只证明检查任务在运行，不等于网络一定通畅。可手动执行一轮：

```sh
exitnode watchdog tick
```

返回值：0 表示正常或按配置停用，1 表示正在等待或恢复，2 表示需要人工处理。不要把返回值 2 当成自动重启已经成功。

## 为什么单元文件不设启动频率限制

看门狗是每分钟触发一次的 oneshot 单元，5 分钟 3 次的启动频率限制必然撞上。按 systemd 语义推断，撞限后单元进入 failed，journal 报 `start request repeated too quickly`；定时器照常走，但检查任务不再运行。本次去掉看门狗服务与定时器单元中的这两项限制，改由 `check` 的十分钟记录新鲜度与服务 `Result` 核查兜底；`Result` 为 `start-limit-hit` 时判失败。

## 临时关掉与恢复

临时停止后续定时检查：

```sh
systemctl stop exitnode-watchdog.timer
```

已经开始的一轮可能仍在运行。如需连手动检查的恢复动作也停掉，将配置 `[watchdog]` 下的 `enabled` 改为 `false`。只想禁止整机重启，则改 `reboot_enabled = false`。这两个设置不关闭独立的硬件看门狗。

恢复时将 `enabled` 改回 `true`，然后运行：

```sh
systemctl start exitnode-watchdog.timer
```

配置路径不是默认值时，在命令前加 `--config /实际配置路径`。默认参数与全部可调整字段见示例配置中的 `[watchdog]` 段；整机重启的持续失败门槛不得小于五分钟。

## 硬件看门狗与撤回

安装时默认检查 `/dev/watchdog`。不存在就明确记录跳过，不算安装失败。存在且 `hardware = true` 时，写入本项目的系统管理配置，设置 60 秒硬件喂狗间隔和十分钟重启看护，并重新加载系统管理进程。已有同名文件而不属于本次安装清单时拒绝覆盖。

硬件看门狗由系统管理进程维护，独立于每分钟的检查。修改 `hardware = false` 只影响后续安装，不删除已安装的设置。需要移除时使用安装撤回或卸载流程；它会按清单逆序移除本项目硬件配置、重新加载系统管理进程，并停用定时器。撤回或卸载也会影响本项目其他安装步骤，执行前应确认维护范围。第二次安装不会重复执行已经完成的命令。

## 重启前先清除启动限制

隧道服务的单元带有 `StartLimitBurst=3` / 300 秒的启动限制。内核连续崩溃时约 10 秒就会撞上，此时直接 `systemctl restart` 会被 systemd 拒绝，但这次重启额度已经计入。因此看门狗在重启隧道服务之前，以及回滚配置后重启之前，先执行一次 `systemctl reset-failed <单元>`。reset-failed 失败（返回非 0）不影响后续重启，也不记录命令输出，不改变状态。

## 时钟异常

系统时间曾跳到未来再拨回时，状态里会残留“未来时间戳”，让冷却与额度永久不满足。判定口径：时间戳比当前时间晚超过 300 秒才算未来时间戳，300 秒以内（例如网络对时的小幅校正）视为正常。每轮检查开头，看门狗把重启、回滚、整机重启的记录以及其他时间字段中的未来时间戳按失效丢弃：重启记录直接删除并同步窗口计数，`first_failure_at` 重置为当前时间（连续失联时长从现在重新计，回拨不会立刻满足 30 分钟整机重启条件），其余字段置空。有改动时记一条 `clock_adjusted`。已有的动作历史不改写，记录中不含凭据。

## 本单不包含的内容（nonGoals）

- 每周例行重启仅保留 `weekly_reboot = false` 配置项；即使改为 true，本版本也不生成任何每周重启单元。
- 不增加隧道内核心跳；进程自身崩溃由原有服务重启机制处理。
- 不实现入口发布、自动开端口、动态域名、更新器或独立救援服务。
- 不改变设备发放、隧道配置生成或证书分发；不操作其他项目的服务或网络规则。

- 把系统时间拨快一天，触发一次重启后再拨回，下一轮检查应记 `clock_adjusted`，且恢复动作不被锁；尚未实测。

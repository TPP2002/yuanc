# 节点救援单元维护说明

救援程序只管“节点程序本身坏了”。它保留独立代码和本地出厂稳定包，不依赖更新器，也不访问网络。主程序正常但宽带、路由器或上游断网时，它不会重装程序。

## 什么时候会动手

开机约三分钟后开始检查，以后每五分钟一次。每轮检查当前版本链接、清单逐文件哈希、主程序能否导入、内核能否运行、配置能否通过内核检查，以及代理服务是否进入失败状态。导入检查最多三十秒。

- 程序完整性、导入或内核运行连续两轮失败：用出厂稳定包重装；第一轮只记录。
- 程序前三项正常，但配置连续两轮失败：恢复最后一份经过检查的可用配置。
- 程序和配置都正常，但代理服务连续两轮处于失败状态：解除失败状态并重启代理。
- 全部正常：清空失败计数。快速重复执行不会增加轮数，两次计数至少相隔五分钟。

重装六小时最多一次，二十四小时最多两次；解除失败状态并重启每小时最多一次。尝试开始前就记入额度，失败和中断也计数，超限会显示“需人工处理”。自己的状态记录损坏时也停止恢复，避免丢失历史后突破次数限制。

更新器持有更新锁时整轮跳过，不清理、不写状态、不执行恢复。看门狗显示需要人工处理时只记录，不因网络故障重装。看门狗记录损坏按不存在处理。

## 动手具体做什么

先检查出厂包清单及全部文件哈希。出厂包坏了就报告人工处理，不修改程序、配置和服务；仅保存救援状态及失败记录。

出厂版本已经存在且完整时复用；同版本内容坏了才移除重建。复制到暂存目录、再次校验后发布，再通过临时链接替换当前版本。若最后可用配置存在且检查通过，复制到临时文件，复查该副本后替换现用配置。然后重新加载服务定义，并重启本项目的代理、管理面和看门狗定时器。最后复查程序完整性、导入、内核和配置，全部通过才记录恢复成功，否则报告人工处理。

没有可用备份配置或检查不通过时，单独的配置恢复会停止并保留现用配置。重装时没有可用备份则不覆盖现用配置，仍以重装后的复查结果判断成功。

套用副本前，先读取设备登记表 `/var/lib/exitnode/secrets/devices.json`，按未吊销名单剔除副本里已吊销或不在名单上的用户记录。登记表不存在时按空名单处理；损坏时单独恢复配置会停止并转为“需人工处理”，现用配置保持不变。重装遇到登记表损坏时仍继续重装程序，但不恢复配置；现用配置若仍有故障，最后复查会失败并转为人工处理，不能把程序重装完成当成服务已恢复。

原始副本保留，两次内核检查都针对过滤后的内容，只有检查通过才替换现用配置。成功恢复后提示“已剔除 N 条不在登记表上的用户记录”：剔除 N 条用户记录（同一台设备在主通道与备用通道各算一条），状态与历史不记录设备标识或凭据。

## 独立存放与目录交换

- 代码：`/opt/exitnode-rescue/exitnode_rescue/`。
- 出厂稳定包：`/opt/exitnode-rescue/factory/`，包含整个版本目录及 `manifest.json`。
- 状态和历史：`/var/lib/exitnode/rescue/state.json`、`history.jsonl`，权限均为 `0600`，临时写入后替换。记录中不保存隧道配置内容、凭据或内核命令输出。

目标不存在时直接换名；目标存在时优先使用 Linux 的 `renameat2(RENAME_EXCHANGE)` 交换，再删除旧副本。系统不支持交换，或返回约定的不支持错误时，退化为先把旧目录改名成 `.old-<时间戳>`，再把新目录改成目标名。这种退化方式两次换名之间有短暂空窗，不能当成无间隙原子交换。

下轮检查在更新锁空闲后先恢复残留：目标消失而旧副本还在时先还原旧副本；目标已经存在时清理旧副本，再清理暂存目录与临时链接。清理只在本项目的程序根目录、版本目录、救援根目录及救援状态目录内进行，不扫描整机。任何文件操作错误都转为人工处理；如果磁盘本身不可写，可能无法保存状态和历史，应结合命令退出状态及服务日志排查。

## 怎么看状态

主程序正常时：

```sh
exitnode rescue status
exitnode check
```

主程序已经损坏时走独立入口：

```sh
PYTHONPATH=/opt/exitnode-rescue python3 -m exitnode_rescue status
PYTHONPATH=/opt/exitnode-rescue python3 -m exitnode_rescue tick
systemctl status exitnode-rescue.timer exitnode-rescue.service
journalctl -u exitnode-rescue.service
```

独立入口退出值：`0` 正常，`1` 处理中或更新锁占用，`2` 需要人工处理。主程序的检查会增加“救援单元”一层：定时器运行，且最近二十四小时有状态更新才通过。初次安装后的第一次检查尚未运行前，这一层可能暂未通过。

## 怎样提升出厂稳定包

维护人员确认当前版本值得保留后执行：

```sh
PYTHONPATH=/opt/exitnode-rescue python3 -m exitnode_rescue promote
```

提升前必须通过当前版本的清单哈希检查；复制并复核后整体替换出厂包，历史记录标为 `promoted`。

自动提升要求本轮五项检查都通过，并且同时满足：当前版本不同于出厂包；看门狗状态正常且最近十分钟内更新；更新历史中该版本有成功记录，且成功已满二十四小时。自动提升只更新本地出厂包，不下载或安装新版本，也不更新救援代码。

## 怎样更新救援代码

主程序发布包携带救援源码，但普通升级不会覆盖独立运行的救援副本。只有维护人员明确执行下列命令才更新独立代码：

```sh
exitnode rescue refresh
```

它复制当前运行程序附带的救援源码到同级暂存目录，核对完整文件清单与哈希，使用新的 Python 进程验证能导入暂存副本，再整体替换。校验失败保留原来的独立副本。`refresh-check` 是独立入口的导入检查命令，不执行恢复动作。

`init` 首次安装独立代码和出厂包，启用救援定时器；重复安装跳过已经完成的步骤。`upgrade` 不修改独立救援目录。`rollback`、`uninstall`、`uninstall --purge` 均保留整个 `/opt/exitnode-rescue/`；撤回或卸载会停用并移除本项目救援服务定义，保留文件不代表定时器继续运行。清除凭据会删除配置及其备份，救援包不备份用户凭据。

## 远程进门和不管的事情

维护人员连上隧道后，用 SSH 连接节点的局域网地址。前提是该设备的 `device_id` 已写进 `proxy.maintenance_device_ids`，否则会被节点路由拦下。节点的 nft input 策略是 accept，不拦截 22 端口；仍需节点安装并运行 SSH 服务，且维护人员持有有效登录凭据。隧道本身不可达时，这条入口也不可达。反向 SSH 等客户服务器到位后另立卡，本单不部署该能力。

救援不修运营商或家庭路由器断网、不处理硬件损坏或断电、不回退操作系统镜像，也不设置定时检查更新。主程序与救援程序同时损坏、磁盘损坏等情况需要人工进入或现场处理。

## 时钟异常

系统时间跳到未来再拨回后，救援状态里的重装与重启时间记录可能晚于当前时间。晚超过 300 秒的记录视为未来时间戳：不计入频率额度，且每轮开头从状态里剔除，并在历史里记一行 `clock_adjusted`（原因文案不变）。300 秒以内按正常处理。额度数值不变。

## 真机待验证

本工位只使用模拟主机进行自动验证，下列项目尚未在 Debian 真机执行，不作为已通过：

- 吊销一台设备后人为触发一次回滚（或救援恢复），确认被吊销设备仍连不上。

- 把系统时间拨快一天，触发一次重启后再拨回，下一轮检查应记 `clock_adjusted`，且恢复动作不被锁。
- 独立目录安装、真实文件权限、复制后的可执行权限、服务启停及定时器触发时间。
- glibc `renameat2(RENAME_EXCHANGE)` 在实际 ext4、xfs、btrfs 或 tmpfs 上的行为，以及不支持时的两步换名路径。
- 两步换名中间杀进程或断电后旧目录恢复；真实存储同步和磁盘写满错误处理。
- 实际更新锁竞争、Python 导入超时、内核检查、损坏程序后的重装和服务恢复。
- 隧道内 SSH 登录与真实外网出口恢复。

这些是本单交付的待验证清单，不另立卡，不将模拟测试当作实机验收。

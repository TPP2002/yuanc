## 一、结论

1. 全部流量模式下,没有找到让流量绕过隧道直接发往公网的路径(第二节)。
2. 找到一处缺口:隧道内核没在跑而保护还在时,域名查询可以经路由器外发;泄漏检测工具查不出它。已修并合并(PR #83),卡 SEC-WIN-LAN-DNS-LEAK-1127;真机上结束内核后的抓包还没做。
3. 找到一种客户端查不出来的情况:电脑开着系统代理时,浏览器的流量先交给那个代理,自检照样全过。已加自检第十二项并合并(PR #85),卡 WIN-SELFCHECK-SYSTEM-PROXY-1127;真机上开着系统代理连接的那一步还没做。
4. 有十二条按设计不管或做不到的边界(第四节),交付时要对客户讲明。
5. 请独立审稿人只看代码再挑一遍,另找到五处隐患,都已立卡、还没修(第三节第 5 小节)。其中三处和出口保证有关:连着时网卡新拿到公网地址只提示、开机时配置文件丢了会撤保护、停在「需人工处理」后巡检停掉。
6. 以上是读代码的结论。客户端连上节点后的整条链路至今没有做过一次真机测试,能不能说「确保」,要看第六节的真机抓包。

## 三、缺口与处理

### 1. 内核没在跑时,域名查询可以经路由器外发(已修,PR #83)

断网保护放行整个局域网,不限端口。电脑的域名服务器通常就是路由器,所以发往路由器 53 端口的查询在保护层是放行的。隧道内核在跑时,内核自己另挂了一条 53 端口阻断,但它随内核进程一起消失。内核不在而保护还在的时段有四种:重连退避的 2~60 秒、停在「需人工处理」或「需重新登录」、后台服务重启或升级、开机后隧道就绪之前。这些时段里的查询由路由器转给所在地运营商的解析器,系统还会缓存拿到的结果。设计正本 §6 写的是「DNS 不单独放行,全走隧道」。

处理:过滤层在局域网放行之上加两条「远端 53 端口阻断」,回环、隧道地址、节点、鉴权的放行排在它前面。契约 `docs/plans/yc-wfp-dns-guard-1127.json`。

防火墙规则那一层没有加同样的阻断:过滤层装不上时,首次连接本来就拒绝连接;已经持有保护又装不上时,界面有告警。

### 2. 泄漏检测查不出上面这种包(同一张单)

`--leak-check` 把局域网对端一律算放行。改成:全部流量模式下,发往局域网对端 53 端口的包记为可疑,终端摘要多一句说明。

### 3. 开着系统代理时自检全过(已修,PR #85)

系统代理、自动代理脚本、命令行代理环境变量开着时,浏览器和命令行程序先把流量交给那个代理。那个代理在本机(别的代理软件)时,对方网站看到的是它的出口;它已经退出时,网页打不开。客户端的出口核验只测后台服务自己,十一项自检照样通过。

处理:自检加第十二项「未设系统代理」,开着就标未通过并点名是哪种设置。只报告,不改用户的设置。契约 `docs/plans/yc-selfcheck-proxy-1127.json`。

### 4. 修复单的本机实测(2026-11-27 晚)

在开发机用测试专用的过滤层(只碰保留地址 `192.0.2.0/24`,不装正式规则)跑了六项真机门控用例,全部通过。其中新加的一项验证了先后次序:发往测试地址 53 端口的 TCP 连接立即被拒;同一地址别的端口不被拒;精确放行地址的 53 端口不被拒。

UDP 的结果要单独说:Windows 在这一层拦下 UDP 包时不向发送的程序报错,程序看不出来。三轮实测里,系统过滤层的丢包事件都记下了「UDP 发往测试地址 53 端口,被同一条过滤器丢弃」,所以修法对 UDP 生效;原用例里「UDP 应当报错」的判断不成立,已改。

这只证明过滤器本身按设计工作,不代替第六节在真机上结束内核进程后的抓包。

### 5. 独立复核补充的发现(已立卡,未修)

请独立审稿人只看代码、不看本记录的结论,重查一遍「全部流量模式连接过一次之后,有没有包能绕出去、有没有状态会悄悄撤保护」。它确认了第二节的路径,另提了九条;逐条对过代码后,五条立卡:

| 卡 | 现象 | 触发条件 |
|---|---|---|
| SEC-WIN-NIC-PUBLIC-ADDR-MIDSESSION-1127 | 连着时网卡新拿到公网 IPv4,只换一句提示,连接照旧;新出现的公网 IPv6 要等 60 秒巡检才关。不吃浏览器策略的软件读得到这个地址 | 连着时电脑自己拨号、插上网卡或手机共享、换到直接分公网地址的网络 |
| SEC-WIN-STARTUP-NO-SOURCE-DROPS-PROTECTION-1127 | 上次连着,开机时找不到配对文件(或登录凭据),三层保护被撤,恢复直连 | 配置文件被清理软件或误操作删掉后重启 |
| SEC-WIN-PATROL-STOPS-WHEN-PARKED-1127 | 停在「需人工处理」或「需重新登录」时保护还在,每分钟的巡检全停 | 内核连续崩溃、节点地址变了、账号到期 |
| WINCLIENT-UPDATE-AUTH-PATH-ROLLBACK-1127 | 邀请码版自动更新后,登录服务器的放行还绑着旧版程序路径,新版连不上,更新回滚,6 小时后再来一遍 | 发布任何一个客户端更新之后;自用版不受影响。读代码得出,未实测 |
| WINCLIENT-KERNEL-ORPHAN-1127 | 后台服务异常退出后旧内核没人管,新旧两个内核抢虚拟网卡,状态来回跳 | 后台服务崩溃或被强行结束。实际表现未实测 |

没立卡的三条:

- 邀请码版的后台服务从物理网卡直连登录服务器。按设计如此,登录服务器与节点是同一台机器、同一个地址;若以后分开部署,这条直连就要写进边界。
- 防火墙层失效时,过滤层单独兜底的局域网范围是整段私网地址,比防火墙的「本地子网」宽;动态地址分配的放行不限远端。不立,因为要防火墙层先失效才有影响,那时界面有告警。
- 维护开关 `wfp-off`、`route-off` 存在时界面没有提示。不立,因为开关目录只有管理员能写,只在我们自己排查时用。

### 6. 没立卡的观察项

- 内核的隧道网卡会往系统防火墙加一条入站放行规则「sing-tun (内核路径)」,名字不在本项目前缀内,断开与卸载都不清。它只放行发给内核进程的入站连接,不影响出口;卸载清理单可以顺手带上。不立,因为没有受害场景。
- 节点路由的第一条「先解析域名」没有限定地址族,节点所在网络有公网 IPv6 时,域名目的地可能从 IPv6 出口出去。本项目客户端只送 IPv4 数字目的地,用不到。已留言给节点装机卡。

## 四、边界:按设计不管,或做不到

交付时要对客户讲明。

1. **仅指定程序模式**:名单外的程序按定义直连。客户的硬要求只有全部流量模式能满足。
2. **没连接时不保护**:装好后第一次连上之前、用户点了断开之后,电脑照常直连,开机自启的软件也是。上次是连接状态的,重启后保护保持,但系统防火墙服务启动前的那几秒不在保护内。
3. **桥接方式的虚拟机**(VMware / VirtualBox 桥接、Hyper-V 外部交换机):等于局域网里的另一台电脑,不经过本机的隧道与保护。
4. **虚拟机或 WSL 里手工把域名服务器指到路由器**:查询经系统 NAT 直接到路由器,本机的防火墙与过滤层都管不到。默认配置不受影响。
5. **局域网是放行的**:打印机、NAS、路由器管理页照常能用。所以局域网里的代理设备、旁路由,本机别的代理软件、系统代理,都能把流量从别处带出去。自检第十二项只提示,不拦。
6. **向路由器问公网地址的软件**(下载软件、Tailscale、Syncthing、部分游戏):它们问到的是所在地宽带的地址,可能自己报给对方。
7. **网络以外的线索**:账号登录记录、Cookie、手机号、支付信息、系统的 Wi-Fi 定位不在本产品范围。浏览器一侧只管 Chrome 与 Edge 的语言、时区、定位授权、实时通信,见 `docs/winclient/环境一致性说明.md` 的承诺边界。
8. **网页邮箱的邮件追踪**:图片由邮箱服务商的服务器代取,对方看到的是服务商的地址,与本产品无关。电脑上的邮件客户端加载图片、收发信走隧道。
9. **手机**不在保护内,手机端未做。
10. **对方看到的是澳洲那条家庭宽带的公网地址**:由运营商分配,可能变;那条宽带若在运营商级内网之后,出口地址与别的用户共用,入口也进不来。
11. **自带网卡驱动、直接往网卡写包的工具**(装了 npcap 的扫描与发包工具):包不经过系统的连接层,防火墙与过滤层都看不到。普通程序、浏览器、命令行工具不属于这一类。
12. **电脑自己拨号上网时拒绝连接**:网卡上直接有公网 IPv4 地址(电脑不经路由器、自己拨号)时,软件能直接读到这个地址,客户端拒绝连接并点名网卡,要改由路由器拨号。交付前要问清客户的电脑是怎么上网的。

## 五、稳定性风险

| 风险 | 现状 |
|---|---|
| 澳洲宽带的公网地址变了 | 配对文件里写的是数字地址,变了就连不上,要在节点重新导出、客户端重新导入;分发版同样连不上(卡 AUTH-NODE-HOST-STATIC-1117 未修)。客户 2026-10-22 说不用域名 |
| 入口靠路由器自动开端口 | 路由器不支持 UPnP 或关着时要手动转发;运营商级内网下进不来。到客户现场才能核实 |
| 节点连不上而内核还在 | 界面仍显示已连接,用户看到的是「连着但打不开网页」;几轮出口核验无结果后界面提示无法核验。节点恢复后自动恢复 |
| 内核连续崩溃 | 约 7 分钟后停在「需人工处理」,要用户点重连。保护保持 |
| 后台服务异常退出 | 旧内核成为没人管的残留进程,状态来回跳,要重启电脑(卡 WINCLIENT-KERNEL-ORPHAN-1127,未修) |
| 邀请码版自动更新 | 很可能每次都回滚,每 6 小时断网约 3 分钟(卡 WINCLIENT-UPDATE-AUTH-PATH-ROLLBACK-1127,未修)。发布第一个更新之前要先修 |
| 节点的解析上游 | 只有 1.1.1.1 一个 |
| 握手特征 | 与真实浏览器有已记录的差距,见 `docs/node/握手特征核对记录.md` |
| 中国到澳洲这一段 | 穿透、丢包、延迟、长时间稳定性,在负责人这里测不了(见第七节) |

## 六、交付前真机检查表

判定只看抓包:物理网卡上除了发往节点地址的包和局域网里的包,没有别的,才算通过。工具是客户端自带的 `--leak-check`,退出码 0 为通过,用法见 `docs/winclient/泄漏检测说明.md`。界面上也有入口:「更新与诊断」页的「开始检测」(2026-11-28 加,固定抓 120 秒,真机上还没点过);要自选时长、指定节点地址或保留抓包文件时用命令行。

准备:一台手头没有要紧工作的 Win10 或 Win11 电脑,装 Chrome 或 Edge,最好再装 WSL2 或 Docker;节点已装好、入口能连。

全部流量模式,每一步都跑一次检测:

1. 连上后正常用两分钟:浏览器开 WebRTC 与 DNS 检测页,命令行里 curl、ping、nslookup,开邮件客户端,WSL 与容器里各发几次请求。
2. 检测中途结束内核进程,等 30 秒。(修复单已合并,要用 2026-11-27 之后打的包才查得出 53 端口的包。)
3. 断开 Wi-Fi 或拔网线,十秒后接回。
4. 关掉节点两分钟再开。
5. 重启电脑,登录后立刻检测。
6. 停止后台服务,再启动。
7. 开着系统代理连接:自检第十二项应为未通过。(自检单已合并,要用 2026-11-27 之后打的包。)
8. 点断开:恢复直连,本项目的防火墙规则、过滤器、兜底路由全部清掉。
9. 卸载:同上,另核「sing-tun」入站规则是否残留。

从中国一侧(负责人这里做不了):

10. 三个不同来源的地址查询网站显示的都是节点的公网地址。
11. 连续挂 24 小时,记断线次数和每次自动恢复用了多久;晚高峰测一次速度。

各份说明文档末尾的「真机待验证清单」合计 75 条,本表是其中与出口直接相关的最小集合;其余在卡 WINCLIENT-REALMACHINE-ACCEPT-1022 里做。

## 七、现场查看(2026-11-27 晚)

- 开发机直连的出口与节点的出口是同一个澳洲地址:节点现在放在负责人家里,负责人的宽带本身就在澳洲。所以在这里测,「查到的地址是不是澳洲」分辨不了漏没漏,只能看抓包;配对文件里的节点地址若填局域网地址,自检第二项「出口与节点一致」会显示不一致,这是摆放位置造成的。
- 开发机的系统防火墙三个配置档现在都是关闭状态,没有装客户端。在这台机器上做断网保护实测会打开防火墙并切换全机出口,要先安排。
- 节点上名单同步服务处于失败状态,入口发布模式写的是未实现的值,状态命令提示入口、代理与真实出口未接入。已留言给卡 NODE-REALMACHINE-INSTALL-1127,本次没有动节点。
